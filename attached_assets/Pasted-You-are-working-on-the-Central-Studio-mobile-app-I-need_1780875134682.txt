## 4. New Booking Policy

The app should support two booking types:

### A. Single Class Booking

This is for booking one class only.

Flow:
1. User selects dance type
2. User selects an available class from the published schedule
3. Schedule data should come from the system/backend
4. User confirms booking
5. User pays online or chooses pay at studio if available
6. Booking is added to user bookings

Single class booking should use the available classes published by the admin/system.

---

### B. Bundle / Package Booking

Create a complete Packages system.

Users can buy packages such as:
- 4 classes
- 8 classes
- 12 classes
- The system should support unlimited package sizes in the future

Rules:
- Each package expires 6 months after purchase.
- A package is not restricted to one dance type.
- Example: User buys a 4-class package and can attend 4 different dance styles.
- The user can use package credits to book available classes.
- Each class attendance should deduct 1 credit from the package balance.
- Packages should be displayed in the new “Packages” bottom nav tab.

Packages screen should include:
- Available packages
- Package name
- Number of classes/credits
- Price
- Expiry period: 6 months
- Buy package button
- My active packages
- Remaining credits
- Expiry date
- Package usage history

Booking with package flow:
1. User selects a class
2. User chooses payment method
3. If user has active package credits, show option: “Use Package Credit”
4. If selected, reserve the class using 1 credit
5. Credit should only be deducted when attendance is confirmed, not just when booking is created, unless the admin policy requires otherwise.
6. Show package balance after booking/attendance

## 6. Ballet Section — Separate Flow

Create Ballet as a separate section, not a normal dance class booking flow.

Ballet has special rules.

Ballet should not be booked directly like other classes.

When user chooses Ballet, send them to a Ballet Assessment page.

### Ballet Flow:

1. User selects Ballet
2. App opens Ballet Assessment page
3. User fills application form
4. User selects available assessment appointment from backend/system
5. User submits application
6. Application status becomes Pending Assessment
7. Admin/system reviews and updates result
8. User receives push notification with result:
   - Accepted
   - Rejected
   - Needs Follow-up
9. If accepted, the system assigns the user to a Ballet level and class schedule
10. User can then see assigned ballet classes in My Bookings / Classes

### Ballet Levels:

Ballet has:
- Pre-Ballet
- Ballet Level 1
- Ballet Level 2
- Ballet Level 3
- Ballet Level 4
- Ballet Level 5
- Ballet Level 6
- Ballet Level 7
- Ballet Level 8
- Ballet Level 9

### Ballet Packages:

Pre-Ballet:
- 8 hours monthly
- 1,950 EGP

Ballet Levels 1–9:
- 12 hours monthly
- 2,650 EGP

### Ballet Assessment Form Fields:

Since most applications will be submitted by parents, create a parent-friendly form.

Required fields:
- Parent full name
- Parent phone number
- Parent email
- Child full name
- Child birthday
- Child age
- Child gender
- Previous ballet/dance experience: Yes / No
- If yes, describe experience
- Medical notes or injuries
- Preferred assessment date/time
- Emergency contact name
- Emergency contact phone
- Notes

Assessment appointment data should come from backend/system availability.

### Ballet Statuses:

- Not Applied
- Application Submitted
- Pending Assessment
- Accepted
- Rejected
- Needs Follow-up
- Assigned to Level
- Active Ballet Student

## 8. Attendance System + Package Credit Deduction

Create the structure for an attendance system.

Recommended approach:

### Option A: QR / Barcode Attendance

Each booking should generate a unique QR code or barcode.

At the studio:
- Instructor/admin scans the user’s booking QR code
- System marks attendance as Attended
- If booking was made using a package, deduct 1 credit from the package balance
- If booking was single paid class, mark as attended only

### Option B: Admin Manual Attendance

Admin/instructor opens the class attendance list and marks:
- Attended
- No-show
- Cancelled

If Attended:
- Deduct 1 package credit if applicable

### Recommended MVP:

Implement both structure-wise, but prioritize Admin Manual Attendance first because it is easier and more reliable for MVP.

Prepare QR/barcode logic for the next version.

Attendance statuses:
- Booked
- Attended
- No-show
- Cancelled

Package credit logic:
- Package has totalCredits
- Package has remainingCredits
- Package has expiryDate
- Credit is deducted when attendanceStatus becomes Attended
- Do not deduct credits for Cancelled
- For No-show, create a configurable admin policy:
  - Deduct credit
  - Or do not deduct credit
